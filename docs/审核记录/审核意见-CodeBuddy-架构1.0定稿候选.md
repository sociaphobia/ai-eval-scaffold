## 三、需求第八节 7 条验收覆盖核查

1. 空项目导入单版、展示要点与可选规则结果、整批合格才保存基线、任一未合格整批不能作回归旧版 → 架构 四:80、八:161/164（未全合格 409）。**覆盖**。
2. 图形界面导入新版、系统读取已接纳基线、单题资格异常暂停整批正式结论但其他可排查、导入缺失/重复/无法配对暂停并列出问题 → 架构 三:60、四:82、八:165/166/169/181/183。**覆盖**。
3. 每题显示输入、要点、两版回答；有规则显示检查结果与疑似退步理由，无规则标待人工确认 → 架构 八:166、五:90。**覆盖**。
4. 确认或改判每题结论；全确认后保存含逐题结论与三数汇总的正式报告；有未确认用例不能生成 → 架构 八:168/169、四:84。**覆盖**。
5. 不调用外部模型服务、不提供评测数据外发通道；未来外发须另行授权 → 架构 一:18、六:100。**覆盖**。
6. 项目方提供通过/失败/误报/漏报/无规则五类样例，评测人员标注题级预期结论；验收展示每类具体题目和数量，所有题仍需人工确认 → 行为层：架构 五:90（误报改判填理由）、八:163/168（人工可纠正自动提示，每题仍人工确认）、七:106（规则单元验证含通过/失败/无规则/触发）、七:112（实际执行结果记通过数，不预写比例）。第七节表格未显式枚举“误报、漏报”两类并引用第八节第 6 条，但行为与验证入口已覆盖，明细核对表按架构 七:112 由开发计划编写。**判定：覆盖（见可选-1）**。
7. 项目方备份恢复权威数据；恢复演练中工具仅在基线回答、接纳记录及对应依据完整且相符时允许正式回归；缺失/损坏/不符暂停并可走重评接纳 → 架构 六:96、四:82。**覆盖**。

## 四、事务与状态可实现性评估

- **整批导入事务**：架构 四:80“先解析和验证完整批次，再原子写入暂存批次及其所有用例；失败即回滚”，配合 八:161/165 的 422 `invalid_import`，可实现“不留半批”（需-11）。可实现。
- **接纳事务**：逐题决策独立保存，仅在所有题合格时于一个数据库事务内写入整批接纳事件并更新当前基线指针；事件写失败则指针不变；服务层复查门禁，不靠前端禁用（四:80）。可实现，满足需-01/需-08。
- **报告事务**：全部题确认、资格通过、当前依据已被项目方确认且必要重新接纳完成时，才在一个事务固化明细与汇总（四:80），八:169 以 409 拦截未满足门禁。可实现，满足需-06/12、验收 4。
- **重新接纳后的回归批次改绑与人工重确认**（四:86）：回归批次导入时记录当时接纳事件标识及当前依据摘要；随后接纳新基线时，在同一接纳事务内检查尚未生成报告的回归批次，仅对用例标识集合及规范化依据都与新基线完全一致的批次改绑新接纳事件，清除旧逐题回归决定并要求重新确认；不匹配批次保持暂停、须修正并重新导入；已保存报告始终引用生成时的接纳事件，不随当前指针改变；输入变化时即使新旧标识偶然相同也视为依据变化，不能凭标识相同跳过新基线门禁。该逻辑为服务层在同一事务内做集合与规范化依据比较及批量更新，SQLite 单写入者下可实现，且与需-08、需求 三:62 的“重新接纳前不按新依据正式回归、保留历次记录”一致。可实现。
- **基线资格核验**（四:82）：核对接纳事件、整批用例数量与标识、依据版本、基线回答、人工结论、误报改判理由及内容摘要的相互对应；摘要采用标准库 SHA-256 对稳定编码内部记录计算，只能检出记录间不一致，不能单独证明被整体篡改的数据可信。与需求 五:125、需-09 一致，边界自认正确。可实现。
- **状态集合**（八:172）：基线批次 `pending/accepted/invalidated`，回归批次 `pending/paused/reported`，配合 409 `workflow_conflict`（八:183）与失效标记（四:82），能表达“暂不接纳、暂停、失格、已报告”。可实现。
