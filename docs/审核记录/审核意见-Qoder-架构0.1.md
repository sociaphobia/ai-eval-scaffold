## 三、关键设计点审查

### 3.1 业务状态与数据库事务衔接

第四节（行 80）明确了三个原子事务边界：
- 导入：完整批次验证→原子写入→失败回滚
- 接纳：全部合格→单事务写接纳事件+更新基线指针→事件失败则指针不变
- 报告：全部确认+资格通过+依据确认+重新接纳完成→单事务固化

服务层二次门禁（行 80 末"服务层再次检查门禁，不能只靠前端按钮禁用"）防止绕过。

**判定**：事务边界与业务门禁衔接清晰，无遗漏。

### 3.2 整批门禁

- 首次接纳：全部合格方可（第四节行 80）
- 回归报告：全部确认+资格+依据确认方可（第四节行 80）
- 导入异常：事务前失败不留半批（第三节行 60）
- 资格异常：阻止整批正式结论（第四节行 82）

**判定**：门禁覆盖完整。

### 3.3 基线资格异常与可信恢复

- SHA-256 摘要检测记录间不一致，明确声明"不能单独证明被整体篡改的数据可信"（行 82）——诚实标注局限
- 恢复流程：隔离→SQLite 完整性检查→业务资格核验→通过才开放（第六节行 94）
- 不可恢复时走重新评测接纳路径（第六节行 94）
- 查实错误接纳：保留原事件+失效标记+重评新基线（行 82）

**判定**：恢复路径完整，可信度边界如实标注。

### 3.4 评测依据变化后重新接纳

- 第四节行 84：输入变化→新用例基线；输入不变要点/规则变化→复用回答→重评→整批合格后重新接纳
- 重新接纳前不能正式回归
- 第八节 `POST basis-confirmation`（行 162）记录项目方确认

**重要建议**：重新接纳的具体接口流程未显式列出。可推断为"导入新依据批次→逐题确认→accept"，但建议在第八节补充一行说明或标注"重新接纳复用 baseline-batches 接口"，避免开发时产生歧义。

### 3.5 单机无鉴权与多项目边界

- 第三节行 56：首版不做账号登录，项目方与评测人员是流程责任
- 第六节行 98：默认绑定 127.0.0.1，不开放公网
- 第九节行 175：风险明确标注"多人环境缺身份边界"
- 多项目共存：第一节行 16 声明"单机、单服务实例"，第三节行 56"一个本机实例可管理多个项目"

**判定**：边界清晰，不越界，未来扩展路径已标注。

### 3.6 SQLite 备份方案

- 第六节行 94：停服后复制，恢复时隔离+完整性检查
- 行 96：选用默认回滚日志模式（非 WAL），引用官方 WAL 文档说明为何不选 WAL（-wal 文件遗漏可能丢数据），引用在线备份文档说明未来不停服方案需专用 API
- 与需求第六节"项目方负责备份、不内置备份调度"一致

**判定**：备份方案与单机停服边界自洽，引用官方文档说明选型理由。

### 3.7 导入文件自证

- 候选 JSON 结构（行 126-145）：`version_label` 只作展示，`case_id` 负责配对，`criteria` 非空，`rules` 可为空，`kind` 枚举二值，`text` 非空
- 第五节三层校验（行 90）：结构→批次→业务
- 第三节"标识在批内稳定唯一"（行 60）
- 需求第六节行 131 明确"用例标识只作配对依据，不证明评测依据一致"——架构未违反

**可选建议**：候选 JSON 未包含格式版本标识字段（如 `schema_version`）。首版单机场景下影响有限，但若未来格式演进（如增加新规则类型），缺少自动判别手段。可作为裁定时讨论项。

### 3.8 前后端依赖方向

第二节分层图（行 22-36）：
- 浏览器 → pages/api（前端内部）→ FastAPI api → service → repository → SQLite
- 明确口诀"页面只调接口层，业务规则只留在服务层，持久化只能经仓储层"（行 38）
- 前端 api 集中请求（引用金融项目 `web/src/api/http.ts:126`，行 38）
- 构建后由同一 FastAPI 进程提供（行 17）

**判定**：单向无环，职责边界明确。
