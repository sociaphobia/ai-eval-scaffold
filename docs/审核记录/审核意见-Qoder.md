## 二、阻断级问题

### B-1：「可信备份」被当成既有前提使用，但没有任何需求规定它由谁、在何时、以什么形式产生

- **证据**：备份只出现在**读取／恢复**一侧，全文零处规定其产生：`需求文档.md:47`（“若能恢复完整且可核验的基线及接纳记录，则恢复后继续；没有可信备份时……”）、`63`、`70`、`88`（需-09“若有完整且可核验备份则恢复后继续”）、`115`、`153`。反向核对：第四节功能需求表 `需求文档.md:80-91` 无“备份”相关条目；第七节首版不包含清单 `需求文档.md:131-135` 也未排除它；第八节六条拟议验收 `需求文档.md:141-146` 无一条覆盖；第九节 `需求文档.md:153` 只把“备份核验方式”标为待确认，未质疑备份本身的来源。
- **影响**：需-09／`需求文档.md:47` 的主路径“有可信备份→恢复后继续”**既不可执行也不可验收**——首版若不含备份能力，该分支永不触发（属自检第 5 问“分支永不触发、无测试覆盖”）；若含备份能力，则这是一项从未被登记、也从未由用户裁定的新增能力，与本项目“小型辅助脚手架”的范围预期冲突（`HANDOFF.md:89` 已把范围失控列为已知风险）。当前稿件把两种可能同时留在文内，架构阶段无论选哪边都能自称符合需求。
- **修订建议（审核方自拟，供用户裁定）**：二选一后回写。
  - 甲：**工具不提供备份**。则改写 `需求文档.md:47,63,88` 为“由项目方自行取回基线回答与接纳记录材料，工具只负责核验其完整性与可核验性”，并在第七节 `需求文档.md:131-135` 增列“备份与保留管理”为不包含项；第九节相应条目改为“材料如何取得由项目方自管”。
  - 乙：**工具提供备份**。则新增需-13 一行，明确备份的产生时机（接纳／重新接纳时同步生成）、备份内容（基线回答＋接纳记录＋当时评测依据）、由谁触发，并在第八节补一条对应验收。

## 三、重要问题

### I-1：已确认的必需输入「用例标识」没进第六节概念数据清单

- **证据**：配对依据已确认为项目方提供的稳定且唯一用例标识（`需求文档.md:64,158`），需-11 对重复与无法配对的检测也依赖它（`需求文档.md:90`）。但第六节的数据清单 `需求文档.md:122` 逐项列了输入、要点、规则、两版回答、接纳记录、改判理由、依据关联、检查线索、回归结论，**未列用例标识**。
- **影响**：第六节是架构阶段推导输入与存储的唯一事实来源，缺一项会在导入契约上必然漏配；同时 `需求文档.md:124` 声明“不指定字段名”，与 `需求文档.md:122` 的清单职责叠加后，读者无法判断标识是“必需输入”还是“实现细节”。
- **修订建议**：在 `需求文档.md:122` 的概念清单中补“项目方提供且整批内稳定唯一的用例标识（仅作配对依据，不证明评测依据一致）”，不指定字段名与承载形式。

### I-2：暂停判据分散在三处、措辞不一，没有统一的触发条件集合

- **证据**：`需求文档.md:47` 与 `88` 枚举“缺失、损坏”；`需求文档.md:115` 另加“与当前旧版回答不符”；`需求文档.md:114,155` 又是一族“接纳记录结论被核实为错误”；而需-02 `需求文档.md:81` 只写“基线资格不能证明时暂停正式回归”。四处分别描述，无一处汇总。
- **影响**：无法判定一次具体异常（如记录在、内容完好、但指向另一份回答）落在哪个分支，也无法为第八节构造完整验收用例；“暂停正式回归”（`需求文档.md:70`）与“暂停新的正式回归”（`需求文档.md:114,155`）两种表述差异未说明是否有意。
- **修订建议**：在第五节下增设一张“资格异常→是否暂停→恢复路径”汇总表，把三类触发条件（材料缺失或损坏、材料与记录不符、记录结论被核实为错误）收进一处，其余段落改为引用该表。同批统一“暂停正式回归／暂停新的正式回归”的措辞或写明区别。此项目前稿件内容已齐备，属生产方可直接完成的整理，不需用户新裁定。

### I-3：异常处置粒度未定义——个别用例异常时是否暂停整批

- **证据**：触发条件按用例个体描述（“基线回答或接纳记录缺失、损坏”，`需求文档.md:47,88,115`），但处置一律写成批次级（“暂停正式回归”`需求文档.md:70`、“整批暂不接纳”`需求文档.md:50,58,72`）。需-11 对导入异常同样取整批口径（“暂停这批评测”，`需求文档.md:90`），而它是**未获确认的自拟建议**。
- **影响**：30 题里 1 题记录受损时，是否禁止其余 29 题继续回归，直接决定工具是否需要用例级门禁与部分可用状态；现稿在此处既无结论，也未被列入待裁定项。
- **修订建议**：把“单题资格异常是否暂停整批回归”列为第九节新的待裁定项（审核方建议保持与整批准入一致的批次口径，但此判断归用户）。

### I-4：回归结论只规定写入，没有任何读取方与用途

- **证据**：保存结论与报告已确认（`需求文档.md:44,66,85`），拟议验收要求含明细与汇总（`需求文档.md:144`）；术语仅说明它与接纳记录用途不同（`需求文档.md:33`）。全文未出现结论的读取方：是否供下一次回归参考、是否跨批比较、是否需导出、是否参与基线判定。
- **影响**：属自检第 2 问“只写不读”。架构阶段容易反向膨胀出一个报告分析模块（超范围），或把它降级成一次性提示（不达验收）；“报告保存成功”也无法客观判定验收。
- **修订建议**：为回归结论补一句用途边界，并在第九节列明“结论是否需跨批查看／导出”为待用户裁定项。

### I-5：“回归前核对评测依据”没有责任主体

- **证据**：`需求文档.md:62` 要求“回归前核对当前评测依据”，但目标使用者分工表 `需求文档.md:18,19` 中项目方只准备输入、要点与回答，评测人员只做导入、复核与保存，无“核对依据”这一动作；`需求文档.md:154` 只写“核对与记录的具体形式待后续设计”。
- **影响**：需-08（`需求文档.md:87`）能否落地取决于这一步由谁执行；形式待定不等于主体待定，现稿实际上没有责任人。
- **修订建议**：在 `需求文档.md:16-19` 分工表补一行责任归属（审核方建议归项目方，判定归用户），并说明工具是否需要在导入时提示“依据已变”。
